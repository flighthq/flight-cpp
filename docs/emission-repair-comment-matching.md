# `insert-using-declaration` must not match a name that appears only in a comment

A repository tooling defect in `scripts/emissionRepairs.mjs`, not a compiler defect.

An `insert-using-declaration` repair fires when its symbol appears in a generated header. The test is a word
boundary match over the whole file, comment lines included. Every generated header begins with
`// Generated by @flighthq/tool-compiler from <package>/<source>#<Symbol> at <revision>`. A refused declaration's
TypeScript is also quoted in `// NOT GENERATED` comment blocks. So a repair keeps "applying" to a header that
names its symbol only in a comment:
- it inserts a `using` declaration;
- it hoists that symbol's defining include into the header.

The expiry check (`obsoleteRepairs`) never sees such a repair as unused.

## How it showed

At flight a627849, `@flighthq/types` no longer declares `Renderer`, `Renderable`, `RenderEffectPadding`,
`RegistryTable`, `CanvasRenderSurface`, `CanvasRenderSurfaceCreator` or `CanvasRenderSurfaceOptions`. The
repairs naming them still fired, for example:
- on `flight/render/renderer.hpp`, whose comment reads `...renderer.ts#Renderer`;
- on `flight/registry/registry_table.hpp` (`...#RegistryTable`).

Each inserted an include of a header that no longer exists, and `pkg:generate`'s dangling-include guard
refused the registry group's move. The entries were removed by hand during the a627849 migration
(see [repin-a627849.md](repin-a627849.md)). The matcher that let them survive was left as it was.

## Reproduction

```js
const header = '// Generated by @flighthq/tool-compiler from @flighthq/x/packages/x/src/renderer.ts#Renderer at abc. Do not edit.\n'
  + '#pragma once\nstatic_assert(flight::runtime_contract.cpp_abi == 1, "...");\n\nnamespace flight::x {\n\ninline void f() {}\n\n} // namespace flight::x\n';
applyEmissionRepairs([{ kind: 'insert-using-declaration', symbol: 'Renderer', ... }], [{ path: 'flight/x/renderer.hpp', contents: header }]);
// before the fix: applied to 1 file, `using flight::types::Renderer;` inserted
```

Both shapes of the kind reproduce it: the single `symbol` form and the `symbols` list form.

## Required behavior

A symbol counts as used only where it appears outside the generated provenance comment. A repair whose symbol
appears only there matches nothing, and a full run then reports it as obsolete. (Quotation comments are a separate
question; see the last section.) Two things stay unchanged:
- a repair that declares `requiredText`, which deliberately witnesses a `NOT GENERATED` marker;
- every other repair kind.

## Fix

`usingDeclarationSymbolText` in `scripts/emissionRepairs.mjs` removes the generated provenance line,
`// Generated by @flighthq/tool-compiler from ...`, before either `insert-using-declaration` shape tests for its
symbol. Nothing else changes:
- every other comment is read as before;
- `requiredText` repairs are unaffected;
- no other repair kind is touched.

`scripts/emissionRepairs.test.mjs` covers the fix with five cases:
- **negative:** provenance-only, for both shapes;
- **expiry:** such a repair is reported by `obsoleteRepairs` on a full run;
- **positive:** an unqualified use in code still fires and hoists the include;
- **idempotence:** a second pass changes nothing;
- **qualified-only use:** no longer fires through the comment.

## Inventory: what changes on the owners' next regeneration

Measured against the committed tree at the time of the fix: for each repair's recorded files, whether the
symbol still appears outside the provenance line once the repair's own `using` line is discounted. Nothing
was regenerated or edited.

Repair/file applications that disappear:

| Repair | Header |
| --- | --- |
| `bitmaptext-unqualified-node-names` | `bitmaptext/update_bitmap_text.hpp` (its only file) |
| `effects-composite-operator-using-declaration` | `effects_wgpu/wgpu_composite_effect.hpp` (its only file) |
| `mesh-unqualified-types-names` | `mesh/vertex_format.hpp` |
| `texture-unqualified-types-names` | `texture/texture_color_space.hpp` |

`bitmaptext-unqualified-node-names` and `effects-composite-operator-using-declaration` then match nothing. A full
run reports them obsolete, which is the expiry check doing its job, so their owners should delete them.

`using` lines that disappear from headers that are otherwise still repaired:
- `audio/audio_resource_reference.hpp`: `AudioResourceReference`;
- `bitmaptext/update_bitmap_text.hpp`: `GlyphMetrics`;
- `scene2d_canvas/canvas_texture_resolver.hpp`: `CanvasTextureResolver`;
- `scene2d_resources/load_scene2_daudio_resources.hpp`: `ExternalAudioResourceReference`;
- `scene2d_resources/load_scene2_dimage_resources.hpp`: `ExternalImageResourceReference`;
- `texture/texture.hpp`: `Texture`.

Each of these also loses the include the repair hoisted. A header that relied on that include for a *qualified* use
of the same type would then fail to compile on regeneration. That would be a loud failure, and the fix for it is an
explicit include repair rather than keeping the comment match.

## Not changed: `NOT GENERATED` quotation comments

A refused declaration's TypeScript is quoted in `// NOT GENERATED` comment blocks, and names appear unqualified
there too. Treating every comment line as non-matching was measured as an alternative. It would change far more:
- 22 repair/file applications would disappear and 3 repairs would become obsolete;
- about 100 headers would each lose `using` lines;
- each of those also loses its hoisted include, so some qualified uses would stop compiling, and that can only be
  verified by regenerating the owners' rows.

So it was not done. Whether quotation comments should count is a separate decision.
